# Design Note — Mode B as an Overlay on a Clean Mode A Spine

*Destination in repo: `shared/docs/DESIGN-NOTE-modeb-overlay.md`*
*Status: PROPOSED architecture for the next Mode B build. Not yet implemented. Captured 7 June 2026.*

## The idea (Peter's brainwave)
Stop trying to slot Mode B clips into the timeline as PEERS of Mode A (which forces the assembler to
compress/extend Mode A around them — the same kind of timing-juggling that produced the silence
complexity we deleted). Instead:

1. When authoring, flag the Mode B phrases but keep them ALSO as Mode A beats — i.e. the promoted
   phrase exists in BOTH a Mode A beat and a Mode B beat (duplicated on purpose).
2. Run the whole pipeline as normal: generate the one continuous audio, all Mode A stills/clips, and
   all Mode B clips.
3. ASSEMBLY PASS 1 — assemble ONLY Mode A against the audio, Whisper-aligned, exactly like the proven
   tiny-test path. The voice is one continuous track; Mode A fills the entire timeline. No Mode B in
   this pass. (This is the assembler we already built and proved — unchanged.)
4. ASSEMBLY PASS 2 — composite each Mode B clip ON TOP of the finished Mode A+audio stream, placed at
   the exact timestamp where its phrase is spoken. Mode B becomes a full-frame OVERLAY that
   temporarily covers the Mode A footage for its few seconds; the audio underneath never changes.

## Why this is a real improvement (the strengths)
- **Separation of concerns.** Mode A aligns to audio cleanly (the thing the assembler does best); Mode
  B is a separate, later compositing step. The two stop fighting each other in one pass.
- **No compress/extend juggling.** Because Mode B COVERS Mode A rather than displacing time, there is
  nothing to stretch or squeeze. The timeline length is set entirely by Mode A + voice. This is the
  same "don't make the pipeline juggle a variable it shouldn't own" lesson as the silence cleanup.
- **The voice stays sacred and continuous** — untouched, one track, exactly as the current model.
- **Graceful degradation (bonus).** Because the phrase is ALSO a Mode A beat, if a Mode B overlay is
  dropped/disabled/fails, the Mode A footage underneath still carries the phrase visually. Nothing
  breaks; you just lose the graphic.

## The honest caveat (what this does NOT solve on its own)
The overlay solves PLACEMENT (where Mode B sits on the timeline), but it does NOT, by itself, solve
WITHIN-CLIP WORD-SYNC (is the on-screen word visible exactly when it's spoken). We proved this session
that Mode B clips currently mismatch on both counts:
- duration overflow (QuoteCard: 157 frames of speech vs a 120-frame component cap), and
- internal-animation lag ("conforming" spoken at 0:30, highlight fired at 0:33).
Overlaying the same clip just RELOCATES that mismatch — it doesn't fix it. The Mode B clip still has
its own internal animation timeline that isn't pegged to the words.

So the overlay idea and the word-sync work are NOT alternatives. The overlay NEEDS the word-sync work
to deliver on its promise. Both must ship together.

## What makes both work: the Whisper timestamps we already produce
`voiceover.json` (word-level Whisper timings, already generated by the audio leg) is the single source
that drives BOTH halves:
- PLACEMENT: when does the phrase START being spoken -> where to drop the overlay on the timeline.
- WITHIN-CLIP FIRE: when is the KEY word spoken (relative to the phrase start) -> when the Mode B
  component's sweep/count/reveal should fire, instead of a hardcoded constant like `sweepStart: 30`.

## Reframed scope for the next Mode B session
NOT "build word-sync" and separately "rethink assembly." Instead, ONE well-scoped build:
**"Build Mode-B-as-overlay compositor, driven by Whisper timestamps — delivers placement AND
within-clip word-fire at once."**

Concretely it implies:
- Authoring/parse: a promoted phrase becomes a Mode A beat (spoken, counts for audio/timeline) PLUS a
  Mode B beat that carries ZERO additional audio time (it must not be double-counted in the read; the
  audio script must speak the phrase ONCE, via the Mode A beat). This is the main parser/audio-script
  wrinkle to design carefully.
- Assembly pass 1: Mode A only, against audio — the existing proven assembler, unchanged.
- Assembly pass 2: a NEW compositing step — ffmpeg `overlay` filter, each Mode B clip placed at its
  Whisper phrase-start timestamp, full-frame, for its clip duration. Real but bounded ffmpeg work.
- Mode B clip generation: the component's internal animation must fire its key beat at the
  Whisper-measured word offset (so the on-screen word lights up as spoken). This is where the actual
  word-sync lives.

## Open questions to resolve when building (don't hand-wave these)
- Audio double-count: exactly how to keep the duplicated phrase spoken once. (Likely: Mode B beat
  flagged `audio:false`/`overlay:true`, contributing video-overlay only, zero to the read/timeline.)
- Overlay duration vs phrase duration: if the Mode B clip is shorter/longer than the spoken phrase,
  what wins? (Probably: overlay covers exactly the phrase's spoken span from Whisper; clip is
  generated/trimmed to that; no freeze-tail juggling because it's an overlay, not a timeline segment.)
- Transition: hard cut to/from the overlay, or a quick fade? (Cosmetic; decide by eye.)
- Does this change the `[B:...]` authoring at all, or is "duplicate into A + flag B as overlay" done by
  the parser automatically from a single tag? (Cleaner if the author writes the phrase once and the
  parser emits both the A beat and the B-overlay beat.)

## Relationship to other banked Mode B work
- Supersedes the old "slot Mode B as a timeline peer + freeze-tail overflow" failsafe approach for the
  word-sync case. (Freeze-tail can remain as a fallback if an overlay is ever missing.)
- Pairs with the banked "design Mode B on the HTML review page" idea: the review page is the natural
  place to confirm/nudge the overlay placement and the within-clip word timing visually.
